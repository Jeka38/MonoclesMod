# Monocles mod — AGENTS.md

## What this is

XMPP chat client for Android — a Conversations fork (via Monocles Chat). Java + Kotlin, Gradle 8.8 / AGP 8.5.2, Kotlin 1.9.10.

## Build

JVM target is 17 (set via `sourceCompatibility`/`targetCompatibility`). Only JDK 21 is installed and compiles fine to target 17. Export `JAVA_HOME` first, e.g.:

```bash
export JAVA_HOME=/home/eugene/.jdks/jbr-21.0.11
export PATH=$JAVA_HOME/bin:$PATH
```

Focused compile/verify (git flavor, debug):

```bash
./gradlew compileGitDebugJavaWithJavac
```

Closest thing to a test suite is lint (this is the CI `test` job — no unit/instrumentation tests exist):

```bash
./gradlew lintGitDebug
```

APKs land in `build/outputs/apk/<flavor>/`. `git/release/` and `playstore/release/` hold local (gitignored) release artifacts.

Build Git (F-Droid) flavor:

```bash
./gradlew assembleGit
```

Build Play Store flavor:

```bash
./gradlew assemblePlaystore
```

Note: the first `assembleGit` invocation occasionally fails on a compile/resource race — re-running the identical command usually succeeds.

## Key gotchas

- **No tests exist.** No `src/test/` or `src/androidTest/` directory. `libs:AXML` has a `// TODO UNIT TESTS` comment.
- **No formatter/static-analysis tasks exist** (no ktlint, detekt, spotless, checkstyle, or `.editorconfig`). Gradle lint (`lintGitDebug`) is the only static check.
- **SDK levels / packaging:** `compileSdk`/`targetSdk` 34, `minSdk` 23 — guard any API newer than 23 behind version checks. Multi-dex and ABI splits (per-ABI version-code offsets, `universalApk`) are enabled.
- **Conversations restored from DB have a null `account` until attached** (`XmppConnectionService.restoreFromDatabase`). During early connection setup (`switchOverToTls`), a live message can be processed against such a conversation. `Message.getContact()`/`Conversation.getContact()` must remain null-safe (they intentionally return `null`/short-circuit when `account` is null rather than NPE). Same rule applies to `Conversation.getBookmark()` and `MucOptions.getProposedNick()` (called from the `MucOptions` constructor via `MessageParser` → `getMucOptions()`), which previously NPE'd on `account.getBookmark(...)`. `NotificationService.push` must likewise handle a null `account` (`message.getConversation().getAccount()` can be null for the restore window): http file-size checks (`HttpDownloadConnection.FileSizeChecker`) run on a background thread and can call `push` on a still-unattached conversation — `push` short-circuits to `pushFromBacklog` for catchup and otherwise **skips** the notification (the notification builder chain derefs the account) instead of crashing. `Conversation.getName()` is likewise null-safe in both branches: the MUC (`nextCounterpart`) branch skips the `account.getXmppConnection()` look-up when `account` is null; the 1:1 branch falls back to the JID local part instead of dereffing a null `Contact`. This covers the `NotificationService.buildMultipleConversation` → `getName()` path triggered by `markRead()` during `switchOverToTls`. `MyLinkify.addLinks(Editable, Account, Jid)` also short-circuits on a null `account`, and the link-preview HEAD probe skips a null `HttpUrl.parse(...)` result.
- **Live 1:1 message dedup:** `MessageParser.onMessagePacketReceived` skips the duplicate check unless the message is a MUC-delay, private, or carries a serverMsgId/remoteMsgId, or catchup is in progress. Re-delivered live messages lacking a serverMsgId rely on `remoteMsgId` matching in `Message.similar()` to be dropped.
- **Data binding + view binding** are both enabled.
- **Translations are Crowdin-managed** (`crowdin.yml`): source is `src/main/res/values/strings.xml`, output `values-%two_letters_code%/`. Only `values-ru-rRU/strings.xml` is a real translation; `MissingTranslation` is disabled, so adding English-only strings builds fine.
- **Signing config** is conditional — requires `mStoreFile`, `mStorePassword`, `mKeyAlias`, `mKeyPassword` project properties. Without them, signing configs are omitted.
- **JVM target:** 17, with Java 8+ desugaring enabled (`coreLibraryDesugaringEnabled true`).
- **Gradle daemon is disabled** (`org.gradle.daemon=false` in `gradle.properties`). Parallel builds are on (`org.gradle.parallel=true`).
- **Lint:** `abortOnError false`; disables `ExtraTranslation`, `MissingTranslation`, `InvalidPackage`, `MissingQuantity`, `AppCompatResource`, `RestrictedApi`. But `StringFormatInvalid` and `StringFormatMatches` are escalated to errors — the only two checks that can fail the build.
- **Layout variants diverge.** `layout-land/fragment_conversation.xml` can differ significantly from portrait. Always update both variants when adding views to `fragment_conversation.xml`.
- **`settings.gradle` references `:libs:xmpp-addr`** but that directory does not exist — only `libs/AXML` is present. This is a stale reference.
- **CircleCI downloads a stale WebRTC `.aar`** (`libwebrtc-m85.aar`) that is no longer used — WebRTC is now a Maven dependency (`im.conversations.webrtc:webrtc-android:119.0.1`).
- **`JingleConnectionManager.getOngoingRtpConnection` returns a `JingleRtpConnection` (an `AbstractJingleConnection`) or an `RtpSessionProposal` — never an `AbstractJingleConnection.Id`.** The "return to ongoing call" intents must test `instanceof AbstractJingleConnection` (as `CallManager.returnToOngoingCall` and `ConversationFragment.returnToOngoingCall` now do). Testing `AbstractJingleConnection.Id` silently matches nothing: the intent gets neither `ACTION_VIEW` nor `EXTRA_SESSION_ID`, so `RtpSessionActivity` starts with `rtpConnectionReference == null`, `updateButtonConfiguration` never runs and the visible hang-up button has no click listener (the call appears unstoppable).
- **The manifest must NOT declare `android.permission.SYSTEM_ALERT_WINDOW`.** No code in the app ever creates an overlay window (there is no `canDrawOverlays`, `TYPE_APPLICATION_OVERLAY`, `TYPE_PHONE`/`TYPE_SYSTEM_ALERT` or similar anywhere) and no dependency needs it, but declaring it makes the **system permission dialog's buttons unresponsive** on ROMs that auto-grant "display over other apps" (EMUI/MIUI): Android's tapjacking protection ignores touches on a permission dialog while the requesting app holds that overlay permission. This was the cause of "the permission dialog's buttons don't work" — do not add it back; if an overlay window is ever genuinely needed, request it at runtime and clear it before asking for other permissions.

## Mod-specific behaviors (do not "fix" back to upstream)

- **File downloads are redesigned:** HTTP transfers save to the **public Download folder** (`Download/<APP_DIRECTORY>/`) using the **original filename**. Name priority is the SIMS `<name>` element (`Message.FileParams.getName()`) first, then the last URL path segment (`HttpDownloadConnection.originalFilenameFromUrl`). Downloaded files show an "Open file" button in the chat.
- The chat shows the original filename under a downloaded/openable file — but **deliberately not** under image/video previews (`displayMediaPreviewMessage`). Do not "fix" the preview to show the name.
- OMEMO-encrypted HTTP downloads and background fetches (link images) are **deliberately not** redirected — they keep private storage/temp paths.
- Legacy Jingle (XEP-0234) transfers intentionally keep the upstream private-storage behaviour.
- `ServiceManagementDialog` derives its action menu from disco#info; if `disco#info` fails (error/timeout) it falls back to showing all actions rather than collapsing to just "Copy JID".
- **MUC conversation name fallback** (`Conversation.getName()`): `muc_name` → bookmark name → **JID local part (before `@`)**. The room topic/subject is deliberately **not** used as a fallback — do not "fix" it back.
- **Notification default is decoupled from MUC privacy/anonymity**: `Conversation.alwaysNotify()` defaults to `Config.ALWAYS_NOTIFY_BY_DEFAULT` for *all* rooms — it does **not** implicitly become true for private non-anonymous rooms. So toggling "make real JIDs visible" (`muc#roomconfig_whois=anyone`) in the conference configurator never flips a room into "notify on all messages" ("individual notifications"); the per-room choice (always / mention-only / mention+reply / never, `ConferenceDetailsActivity` `mNotifyStatusClickListener`) is the only thing that controls it.
- **MUC topic strip** (preference `show_muc_topic`, default `false`): when enabled, `ConversationFragment` shows the room topic in a narrow `muc_topic` strip above the message list (added to **both** `layout/` and `layout-land/fragment_conversation.xml`); tapping it opens the conference details (`switchToMUCDetails`).
- **Per-status presence priority**: edited in **Expert settings → Presence → "Presence priorities"** (`preferences.xml` key `presence_priorities`; `SettingsActivity.editPresencePriorities()` → `showPresencePriorityDialog()`, `layout/dialog_presence_priority.xml`). With one account the dialog opens directly; with several it first asks which account (`choose_account`). One field per presence status — Online / Away / XA / DND (each -128..127, default 50 / 30 / 20 / 10, stored in `Account.keys` via `KEY_PRESENCE_PRIORITY_ONLINE/_AWAY/_XA/_DND`, `getPresencePriority()` / `getPresencePriority(Presence.Status)` / `setPresencePriority(Presence.Status, int)`; CHAT/OFFLINE map to the Online bucket). Saving persists with `databaseBackend.updateAccount(account)` and sends presence immediately (`sendPresence(account)`). **These fields were deliberately moved out of the account editor** — `EditAccountActivity` no longer reads, writes, or has UI for them; do not add them back. `PresenceGenerator.selfPresence()` emits `<priority>` (only when non-zero) for the value matching the account's **current** status — a status change (`changeStatus` → `sendPresence`) picks up the new value immediately, and MUC join presences go through the same path. Saving account options reconnects the account (`updateAccount` → `reconnectAccountInBackground`).
- **Live-location movement track**: a live-location share renders a **polyline** of the actual route, not just the current point. The sender keeps the full history: `MessageParser` stores the *previous geo body* (`getRawBody()`, since `getBody()` is `""` for geo URIs) into the message edits in `LiveLocationManager.correctMessage` (replaced the old trim-to-first-entry behaviour). `GeoHelper.getTrackPoints(Message)` reconstructs points from edit bodies + the raw body (dedups points <10 m apart); `createGeoIntentsFromMessage` adds them as the `track` parcelable-array extra, and `ShowLocationActivity` draws the track as the `Polyline` (blue, 8 dp) and auto-frames it on first display. `LocationActivity.clearMarkers` also removes polyline overlays.
- **Image link previews in chat** (`displayTextMessage`): first tries `extractFirstImageUrl` (URL path must end in a literal image extension), then falls back to `extractFirstUrl` for any http(s) link that dominates the body. Failure to render hides the preview (`onLoadFailed`), leaving just the clickable link.
- **Animated avatar blink fix** (`AvatarWorkerTask`): when `play_gif_inside` is enabled and the avatar cache misses, the original code fell back to an async worker that briefly showed a blank placeholder before the avatar loaded — a visible "blink" on every presence update. The fix tries a synchronous `get(cachedOnly=false)` first so the avatar appears immediately; the async worker is now only used for truly absent avatars (e.g. newly joined occupants without cached vCards).
- **XEP-0144 Roster Item Exchange** (`xmpp/rosterx/`): `RosterItem` (single `<item action jid name><group/>`), `RosterExchange` (parses either the modern `http://jabber.org/protocol/rosterx` **or** the legacy XEP-0093 `jabber:x:roster` namespace — `Namespace.ROSTERX` / `Namespace.ROSTER_LEGACY`), and `RosterExchangeManager` (send + apply). **Send:** "Переслать контакт" in the contact context menu (`contact_context.xml` → `StartConversationActivity.sendContactTo()`) and in `contact_details.xml` (`ContactDetailsActivity`, `action_send_contact`); both open `ChooseContactActivity.createForRosterExchange(...)` (multi-select + enter-JID) and send `<message><x xmlns=rosterx>…` to each chosen recipient. The JID list comes from `ChooseContactActivity.extractJabberIds(result)` (now null-safe). **Receive:** `MessageParser` calls `RosterExchangeManager.onStanzaReceived` right after the counterpart is resolved, but only for live 1:1 traffic (`!fromAccount && !isTypeGroupChat && mucUserElement == null && query == null` — do **not** drop those guards, otherwise MAM-replayed payloads re-prompt on every sync and MUC PMs spuriously prompt); it returns `true` to swallow the stanza so the payload does not become a chat message. The service dispatches to a foreground `OnRosterExchangeRequested` listener (`XmppActivity` auto-registers activities implementing it: `ConversationsActivity`, `ContactDetailsActivity`) which shows `RosterExchangeDialog`; with no listener the exchange is queued in `XmppConnectionService.mPendingRosterExchanges` and surfaced via `NotificationService.notifyRosterExchange` (`ROSTER_EXCHANGE_NOTIFICATION_ID`). `ConversationsActivity.onBackendConnected` drains the queue. **Only `add`/`modify` suggestions are offered** (the dialog drops `delete`-only payloads); applying uses `createContact(contact, true)` after merging groups/name, per XEP-0144's user-confirmation requirement. `Namespace.ROSTERX` is advertised in `AbstractGenerator.STATIC_FEATURES` (so it is in the caps hash); `Contact.getGroupNames()` was added as the public group accessor.
- **Custom emoji ("smiles") and client icons are on by default** (the upstream "stickers" feature is deliberately removed). Smiles live in an **app-private external** `Documents/monocles mod/Smiles/` (falling back to internal `filesDir/monocles mod/Smiles`), **not** the public folder; `icondef.xml` drives name + order, other images in the tree are appended (≤1 MB each) with a `*name*` shortcode. The built-in set is the raw resource `res/raw/smiles_icondef.xml` (`de.monocles.mod.EmojiSearch`). `enable_smiles` swaps the standard emoji2 picker for the custom grid; **Import Smiles (ZIP)** clears the folder to a canonical path before extraction, **Reset Smiles pack** restores the built-in set (`SettingsActivity`). Client icons come from a built-in rule table (`ui/util/ClientIconUtils`), with a read-only fallback to custom icons in `filesDir/client_icons` (`icondef.xml`, matched by XEP-0115 caps candidates, else an inferred client name) — **the import UI for that folder was intentionally removed, so only the read path remains**; `show_client_icons` (default true) puts the icon in the roster list, participant list and details — **the software version string is deliberately hidden in the contacts and participants lists and shown only on the detail screens; do not "fix" it back.**
- **Message search** (`SearchActivity` + `services/MessageSearchTask`, SQLite FTS4 table `messages_index` via `FtsUtils.toMatchString`): tapping a hit opens the conversation and animates the target row (`ConversationFragment.jumpToMessageUuid` → `highlightMessageAtPosition`, an accent pulse that keeps retrying and pages in older MAM history until the message is found). `MessageAdapter.setHighlightedTerm` highlights matching words in the results. Settings has its own search (`SettingsFragment.showSearchDialog`, menu `action_search_settings`).
- **Chat-list and contact grouping.** The chat list has four fixed sections — contacts / transports / conferences / **private messages** (`ConversationAdapter`; order in the `group_order` pref, sections collapsible, persisted in `collapsed_groups`). MUC private messages get their own standalone window: a MUC conversation carrying a permanent `nextCounterpart` (`Conversation.hasPermanentCounterpart()`) is split out of the room by `findOrCreateConversation(..., counterpart, ...)`. On the Start-chat / Contacts tab contacts are grouped by roster **labels** into collapsible `GroupHeader`s (`contacttag:<label>` keys in `collapsed_groups`; unlabeled contacts under `contacts_without_labels`).

## Message Reactions (XEP-0444)

- **Model.** `Message.reactWith(Set<String>)` builds a **hidden carrier** message (`Message.TYPE_REACTION = 7`, `Message.isReaction()`) whose only payload is `<reactions id="…"><reaction>emoji</reaction>…</reactions>` (`Namespace.REACTIONS` = `urn:xmpp:reactions:0`) plus an XEP-0428 `<fallback/>`. The carrier must **never** render as a chat row, bump the chat list, count as unread, or post a notification: `Conversation.populateWithMessages` and `ConversationAdapter.isVisible` filter `isReaction()` rows out, `Conversation.getSortableTime()` uses `getLatestDisplayableMessageTime()` (skips carriers), and `MessageParser` calls `message.markRead()` on live carriers. The old `NotificationService.pushReaction`/`REACTION_NOTIFICATION_ID` path was deliberately deleted — reactions to our own messages surface **only** as the in-chat heart button (`ConversationFragment.reactionJumpButton` → `jumpToLatestReaction`, driven by `Conversation.getUnseenReactionToOwnMessage()` / `markReactionsSeen()` / the `last_seen_reaction` attribute). Do not reintroduce a reaction notification.
- **Aggregation is per reactor, latest carrier only** (`Conversation.getReactionCarriers()` / `getReactionCounts()` / `findReactionsTo()`): in a MUC every occupant is its own reactor (full occupant JID), in 1:1 and MUC PM bodies the bare JID is. `Message.reactionId()` is the target's `replyId()` (server msg-id in a MUC, else remote msg-id) falling back to the local UUID, so a reaction always has a target.
- **Sending.** `ConversationFragment.toggleReaction` sends a fresh carrier (an **empty** carrier removes the reaction, per the XEP); it reuses the conversation encryption and targets MUC PMs via `Message.configurePrivateMessage`. `reactionSendInProgress` makes `messageSent()` skip clearing the composer / scrolling. The picker reuses the composer emoji picker in "reaction" mode and forces the standard emoji2 picker (the custom "smiles" grid and the GIF tab are hidden). "Show reactions" opens `ui/util/ReactionDetailsDialog` (avatar + nickname + emojis per reactor).
- `urn:xmpp:reactions:0` is **not** advertised in `AbstractGenerator.STATIC_FEATURES` (whose only XEP/advertising additions are `Namespace.ROSTERX`, `urn:xmpp:styling:0` and the whiteboard namespaces below), so caps does not claim reaction support even though the client sends and renders it.

## Message Retraction (XEP-0424)

Retracting (withdrawing) a message must be visible to **other clients** as the standardized placeholder, not just deleted locally.

- **Wire format — v1, with v0.3 accepted on receive.** `MessageGenerator.preparePacket` emits the modern **v1** form: a bodyless message with `<retract xmlns='urn:xmpp:message-retract:1' id='…'/>` plus `<fallback xmlns='urn:xmpp:fallback:0'/>` (XEP-0428) and `<store/>`. `urn:xmpp:message-retract:1` **and** `urn:xmpp:message-retract:0` are advertised in `AbstractGenerator.MESSAGE_RETRACTION_FEATURES` (so caps/Hash includes both). `MessageParser` accepts **both** the v1 direct child (`Namespace.MESSAGE_RETRACT`) and the legacy v0.3 `<apply-to xmlns='urn:xmpp:fasten:0' id='…'><retract xmlns='urn:xmpp:message-retract:0'/></apply-to>` (`Namespace.MESSAGE_RETRACT_LEGACY`) — do not drop the v0.3 branch, older peers still send it. The v1 retraction is bodyless; the parser remembers `bodylessRetraction` **before** substituting the XEP-0428 fallback text and tags the carrier `TYPE_REACTION` so it never renders.
- **The retraction targets the id the peers know.** `Conversation.findMessageToRetract(id)` matches the id against the local UUID, the remote/origin-id, the **stanza-id (server msg id)** and previous edit ids — the plain `findSentMessageWithUuidOrRemoteId` used before did **not** check the stanza-id, so a MUC retraction (which addresses the room-assigned `stanza-id`, as in the `<retract id='1792766308589286'/>` example) never matched. The outgoing side sets `retractmessage.setRetractId(target.reactionId())` (stanza-id in a MUC, origin-id in 1:1/PM, local UUID last), the same rule `replyId()`/`reactionId()` use.
- **A retracted row is a placeholder, not a deleted row.** The retracted message keeps `Message.RETRACTED_MESSAGE_BODY` as its body and is **not** flagged `setMessageDeleted(true)`: that flag means "drop the row" — `DatabaseBackend.getMessages` filters `DELETED<?` — so flagging it would make the placeholder disappear after a reload. `Message.hasRetractedBody()`/`isRetracted()` are the markers instead. The sender's own copy is retracted identically (the row is kept, not deleted) so this client shows the same placeholder as everyone else; retracting **somebody else's** message stays a purely local delete (`ownTextMessage` requires `status >= STATUS_SEND`).
- **The placeholder shows the exact retraction time.** `Message.retractedAt` (column `retractedAt`, monocles side table, `monocles.user_version 11`) is set from `System.currentTimeMillis()` on retraction. `UIHelper.retractionTime` formats it as full date + time and the string is `message_retracted` ("Это сообщение было отозвано (%s)"), rendered both in the bubble (`MessageAdapter.getSpannableBody` short-circuits the marker body) and in the chat list (`UIHelper.getMessagePreview`). For old rows without a timestamp it falls back to the sent time, never "just now". **The column must be added in exactly one migration** — it lives on the monocles side table and `monoclesMigrate()` (from `onConfigure`) adds it; the main `onUpgrade` must **not** add it too (that crashed 1.9.1.55 with "duplicate column name: retractedAt"). The main `DatabaseBackend.DATABASE_VERSION` was still bumped to 62; keep it there so devices that already ran the broken 1.9.1.55 (whose main DB rolled back to 61 but whose monocles side table committed `user_version 11`) upgrade cleanly instead of hitting a downgrade.
- **Security.** The MUC retraction condition used to be an unconditional `|| conversationMultiMode`, which — now that the stanza-id is matched — would let any occupant retract anyone's message. `senderMatches` additionally requires the same occupant (or our own session for our own messages); 1:1 keeps the fingerprint/trueCounterpart checks.
- **Menu.** `action_retract_message` and `action_delete_message` both run `ConversationFragment.deleteMessage` (the old `retract_message` handler was a broken duplicate that blanked the body and re-sent it); Retract is offered for our own un-retracted text messages; copy/select/quote/share/notes are hidden for a retracted row so the internal marker body is never exposed.

## Collaborative SVG Whiteboard (Jingle app + XEP-0284 SXE)

A drawing board per 1:1 chat or MUC room, syncable in real time. Opened from the **contact context menu** ("Рисовать с контактом", `contact_context.xml` → `StartConversationActivity.openWhiteboardForContact()`), from the 1:1 conversation's **attach-file menus** — both the overflow submenu (`fragment_conversation.xml` `attach_whiteboard`) and the **composer paperclip quick-attach popup** (`choose_attachment.xml` `attach_whiteboard`) must carry the item → `ConversationFragment.openWhiteboard`, and from inside an active call — the **1:1 call** always-visible on-screen button (`activity_rtp_session.xml` `in_call_action_far_left`, `RtpSessionActivity.updateWhiteboardButton`, shown while `JingleRtpConnection.STATES_SHOWING_ONGOING_CALL` and not in picture-in-picture) and the **Muji call** controls row (`activity_muji_conference.xml` `muji_whiteboard` → `MujiConferenceActivity.openWhiteboard`), which uses the room JID so it lands in the shared room board. All launch `ui/WhiteboardActivity` via `WhiteboardActivity.create(ctx, accountJid, peerJid)`. **The board synchronizes by default:** opening it starts the shared session immediately (`startSharing()` from `onBackendConnected`). Nobody is force-opened any more: a peer learns about a board through the in-chat **"Open board"** notice (`Message.TYPE_WHITEBOARD`) and taps the button. The "Поделиться" (`wb_share`) button just toggles the session off/on.

- **Protocol.** A Jingle application type `urn:xmpp:jingle:apps:svg-whiteboard:0` (`Namespace.JINGLE_APPS_SVG_WHITEBOARD`) over the SXE transport `urn:xmpp:jingle:transports:sxe` (`Namespace.SXE_TRANSPORT`). The shared document is XEP-0284 (`urn:xmpp:sxe:0`, `Namespace.SXE`) synchronized with the record model in `xmpp/sxe/SxeDocument` (`<new>`/`<set>`/`<remove>`, `primary-weight`+RID ordering, last-writer-wins). **Host:** the 1:1 initiator (`session-initiate` → `session-accept`); for a MUC the **room JID is the host** and the SXE payloads travel as `groupchat` messages (the host relays). **A 1:1 invite must target the peer's full JID, never the bare JID** — the server rejects a bare-JID Jingle IQ with `service-unavailable`, so the invite never arrives (no session, no chat notice); `sendJingle` uses `jingleTarget` (`Contact.resourceWhichSupport(NS_WHITEBOARD)`, else `getMostAvailableResource()`, else the bare JID as a last resort), mirroring stanza_im's `_best_full_jid`. `xmpp/whiteboard/WhiteboardManager` (`XmppConnectionService.getWhiteboardManager()`) owns sessions; `xmpp/whiteboard/WhiteboardShape` + `WhiteboardView` are the model and canvas.
- **Wiring.** `JingleConnectionManager.deliverPacket` intercepts the whiteboard description (and any `sid` the manager already knows) **before** the `AbstractJingleConnection` registry and acks the IQ itself — whiteboard sessions must not enter `isBusy()`/the call slot or spawn a `JingleRtpConnection`/call log. **`WhiteboardManager.isWhiteboardJingle` must use `packet.getJingleChild("content")`, not `packet.findChild("content", …)`**: `<content>` is nested inside `<jingle>`, so a direct `findChild` on the packet never matches and the whole whiteboard branch becomes dead (the invite then falls through to the generic Jingle handler and is rejected as `unsupported-info` — no session, no chat notice). Bodyless `<sxe/>` messages are consumed in `MessageParser.onMessagePacketReceived` (live traffic, `query == null`) via `WhiteboardManager.handleSxeMessage(account, packet, live)`, so they never become chat messages — a replayed MAM copy is also swallowed (`live == false`) but does not create a session; `Namespace.JINGLE_APPS_SVG_WHITEBOARD`/`SXE_TRANSPORT`/`SXE` are advertised in `AbstractGenerator.STATIC_FEATURES`. **MUC self-reflections are dropped** (`isSelfReflection` compares the occupant resource with our own MUC nick) — without that every one of our own edits loops back. A received session registers `byPeer` (both the Jingle and the MUC/SXE path) so the auto-opened activity attaches to the **existing** session instead of starting a second one.
- **Handshake.** A joiner sends `<sxe><connect/></sxe>`; the host answers with a `state-offer`, the joiner `accept-state`, then the host pushes the whole document as a `state` (`document-begin` + one `<new/>` per record + `document-end`). **The session id is deterministic** (`sessionIdFor`: SHA-1 of the account/peer, or of the room for a MUC) and **the host is chosen deterministically** (`hostFor`: the account with the smaller bare JID) — this is what makes continuous sync work: with a random per-side `sid` the two ends attached to different sessions and only the initial snapshot ever synced, and with two hosts each side overwrote the other's document. `startSession` is idempotent (returns the running session); a 1:1 board is invited by **whichever side opens it** (the deterministic `host` only governs snapshot duty, not whether an invite is sent — previously only the host invited, so opening the board from the other side silently did nothing); a duplicate `session-initiate` for a session we already hold is accepted without creating a second board or a second chat notice. `Session.joined` makes `joinSession` idempotent (the invite path, the first `connect` and `attachSession` all trigger it); `WhiteboardActivity.onWhiteboardUpdated` also re-attaches when an update arrives for this peer under a different id. `session-initiate` (1:1) and the first `connect` of an unknown MUC session both auto-join and post the chat notice; neither force-opens the screen (the user taps the button) — see below. The tap opens the board via `onNewIntent` (`launchMode=singleTop`). Pressing Share carries anything drawn before sharing into the new document so the local board is not wiped.
- **XEP-0353 Jingle Message Initiation invites (`<propose/>`).** The whiteboard profile's *Full* tier allows inviting from inside an existing chat with Jingle Message Initiation instead of a bare Jingle IQ: the peer sends a **bodyless** `<message type='chat'><propose xmlns='urn:xmpp:jingle-message:0' id='…'><description xmlns='urn:xmpp:jingle:apps:svg-whiteboard:0'/></propose><store/></message>`, and only sends the real `session-initiate` after it receives a `<proceed/>`. A bodyless message *does* reach the Jingle-message loop in `MessageParser` (that loop is inside the `else if (!packet.hasChild("body"))` branch) and is handed to `JingleConnectionManager.deliverMessage` — but **`deliverMessage`'s `propose` handling only accepted all-RTP descriptions** (`rtpDescriptions.size() > 0 && rtpDescriptions.size() == descriptions.size()`), so a whiteboard proposal fell to the "unable to react to proposed session" log and did nothing: no session, no "Open board" button (the exact symptom is an incoming `<propose>` with a whiteboard description and nothing shown). Fixed on **two** levels: (1) `deliverMessage` now calls `WhiteboardManager.handleJingleMessageInitiation(account, from, message)` before the RTP-only branch (gated on `!from.isSelf`), and (2) `MessageParser.onMessagePacketReceived` calls it directly right after the `<sxe/>` handler for live 1:1 traffic (`query == null && !isGroupChat && mucUserElement == null && !fromAccount`) — the second path also closes the short window before `offlineMessagesRetrieved`, when the `deliverMessage` call is skipped entirely. `handleJingleMessageInitiation` accepts `propose`/`retract`/`reject` in `urn:xmpp:jingle-message:0` and returns false for anything else (so RTP proposals and `proceed`/`finish`/`accept` are untouched). `handleProposal` adopts the propose `id` as the session `sid` (XEP-0353 reuses the id for the ensuing `session-initiate`), posts the normal "Open board" notice and answers with `<proceed/>` (`proceedProposal`); a `<retract/>`/`<reject/>` for a proposed (not yet accepted) board drops the session and the notice. The real `dispatchJingle` `session-initiate` (which may use a different sid than the propose) drops any proposal placeholder for that peer first so no duplicate session/notice is left behind.

- **A board start is announced as a normal chat message (1:1 and MUC).** `postWhiteboardNotice` writes a `Message.TYPE_WHITEBOARD = 8`/`Message.createWhiteboardNotice` message with an **"Open board"** button, themed like any message (`layout/message_whiteboard.xml`, view type `WHITEBOARD`, background `message_bubble_received_light`/`message_bubble_sent` + `color_bubble_light`/`color_bubble_dark`), then `markUnread()` + `NotificationService.push` — so it raises the unread badge and a system notification like a normal message. In a MUC the notice lands in the room with the starter's nick (`Session.noticeCounterpart`) instead of an avatar. `getViewTypeCount()` must stay above the highest view type (`WHITEBOARD = 5` → count `6`) or the row silently drops. Deliberately no force-open: the user taps the button.
- **Rooms (MUC) share the same feature.** A room board uses the **room JID as the host**; the SXE payloads travel as `groupchat` and the notice shows the starter's nick. Notifications use the standard `NotificationService.push` → `notifyMessage`, so they **follow the room's notification settings** (muted → silent; mention-only → only on a highlight) — do not special-case the board to always notify. **The old settings-bypassing `NotificationService.notifyWhiteboardInvite` / `WHITEBOARD_INVITE_NOTIFICATION_ID` / `whiteboard_invite_*` strings were deleted** — a board is announced (and notified) only through `postWhiteboardNotice` → `push`.
- **Board payloads carry no body (do not add one back).** A MUC relays a bodyless `groupchat` (our own chat-state messages are bodyless groupchat too) but, unlike one with a `<body>`, does **not** write it to the room history (ejabberd `mod_muc_room.erl` relays unconditionally, then archives only `has_body_or_subject`). An earlier build padded room payloads with an invisible body (U+2063) "because MUC drops bodyless" — that assumption was wrong: the room relayed **and archived** it, so other clients (and our own history after a reload) showed a stray **empty message** per stroke. `WhiteboardManager.send` therefore adds no body and only a `no-store` hint; `isWhiteboardBody` still recognises the legacy U+2063 body (`LEGACY_SXE_FALLBACK_BODY`) so an older peer's payload is swallowed rather than rendered. A replay (MAM) copy is always swallowed by `handleSxeMessage(..., live=false)` — it never creates a session, posts a join notice or sends a `<connect>`. A DB migration (v61) drops messages whose whole body is that invisible separator.
- **The board's creator owns its lifetime; joining must reuse the board.** A room board has no central authority and its session id is derived from the room alone (`sessionIdFor`), so **joining an existing board never creates a new one** — `startSession` returns the running session and `handleSxeMessage` adopts the deterministic `sid`. The **creator** is whoever opened it; that occupant owns the board's lifetime, so **when the creator leaves the room the board closes for everyone**. The creator (full occupant JID) is carried on every `<sxe/>` as `creator="…"` (`sxeElement`, read back by `handleSxeMessage` and `onMucPresenceSxe` via `PresenceParser`), and **`observeMucCreator` keeps the smallest full occupant JID** so all devices converge on the same creator (several occupants can click "start" for the same room; without convergence each would stamp itself and the "creator left" rule would be inconsistent). `PresenceParser`'s `unavailable` branch calls `onMucOccupantUnavailable(account, room, occupant)` for **every** departing occupant (not just non-self), which ends the board when the departing occupant matches `session.creator` — this runs even when the user is not looking at the board. `isOwner(session)` (true for any 1:1 board; for a room, the creator is our own occupant) gates `WhiteboardActivity.onDestroy`: finishing the screen while we are the creator ends the board for everyone (`isFinishing()` guards against a system-initiated destroy). Do not "fix" joining to create a session, and do not make a non-creator's leave end the board.
- **A board end must reach the other side and close the screen.** `endSession(session, broadcast)` (the 1-arg overload passes `true`): 1:1 sends a Jingle `session-terminate`; a MUC sends an explicit `<sxe><close/></sxe>` (client extension of XEP-0284 — a room board has no Jingle session), then (MUC) `clearAdvertisement` re-sends our presence without the `<sxe/>` child and `removeWhiteboardNotices` deletes **every** `TYPE_WHITEBOARD` message in the conversation (not just a remembered uuid — the notice is a local per-device message and a stale one must not survive). `notifyUpdate` + `notifyEnded` fire; `OnWhiteboardUpdate.onWhiteboardEnded(sid)` makes `WhiteboardActivity` detach and `finish()` when it shows that board (so both a local cancel and a peer/room end close the screen). An inbound `<close/>` or `session-terminate` is consumed before a session is created and never echoed.
- **A room board is discovered two ways.** (1) **Groupchat traffic**: the first `<sxe/>` from another occupant on an unknown session creates the session, posts the notice and sends a `<connect>` to ask for the current drawing. (2) **Presence**: an occupant advertises `<sxe session=…/>` in their MUC presence (mirroring `<muji>`); `PresenceParser` forwards it to `WhiteboardManager.onMucPresenceSxe` (called right after the `<muji>` parse), which discovers the board, posts the notice and sends one `<connect>`. The presence path is what lets a **member who joins the room after the board started** see the button (the MUC replays the occupants' presence to them). Our own reflection is skipped (`isSelfReflection`) — `startSession` already posted our notice.
- **A room board must clear its presence advertisement when it ends (and the MUC notice is idempotent).** The MUC service stores each occupant's last presence and replays it to anyone who joins later, so a stale `<sxe/>` made the *"Started a shared whiteboard"* button reappear on **every re-entry** of the room (and for a late joiner) after the board was gone. `endSession` therefore calls `clearAdvertisement(session)` → `sendAdvertisement(session, false)`, which re-sends our room presence **without** the `<sxe/>` child (`advertise` is `sendAdvertisement(session, true)`). `postWhiteboardNotice` is idempotent **for a MUC only**: if the conversation already holds a `TYPE_WHITEBOARD` message it reuses that uuid and returns instead of adding a second button (`Conversation.findMessages(MessageFilter, OnMessageFound)` was added for this). **Do not apply that idempotency to 1:1:** a 1:1 board start is a single event and a stale notice from an earlier board must not suppress the new one, so for `!session.muc` the code deletes every leftover `TYPE_WHITEBOARD` message and posts a fresh one. (Making it idempotent for 1:1 too was a regression: the peer's new board produced no notice at all.)
- **The notice must be posted even when the session already exists.** In `dispatchJingle`'s `session-initiate`, if `sessions.get(sid) != null` (a "duplicate" invite for our deterministic sid), the code still calls `postWhiteboardNotice` when `noticeUuid == null`. Skipping it made the peer's board invisible in a common case: we had opened the board once (`startSession` created the session, and for 1:1 `startSession` deliberately posts **no** notice — only the receiver does), so the peer's real invite looked like a duplicate and no notice was ever posted. Likewise a 1:1 board discovered through the peer's SXE traffic (`handleSxeMessage`, session `== null`, `!isGroupChat`) posts a notice if none exists — otherwise a missed Jingle invite leaves no button.
- **The 1:1 board entry is the overflow `action_whiteboard` ("Start board"), not only the paperclip.** `configureQuickShareAttachmentMenu`/`configureAttachmentMenu` still set the `attach_whiteboard` item visible in the paperclip popup, but the reliable, always-visible entry in a 1:1 chat is `ConversationFragment`'s `action_whiteboard` item (shown for both `MODE_SINGLE` and `MODE_MULTI` in the connected branch; it was accidentally left out earlier, so the 1:1 board was only reachable through the attach popup).
- **A room board has no host and every occupant is a plain participant.** `host` is `false` for every MUC session (`startSession`: `muc || hostFor(...)` — MUC keeps the flag only for the *room relay* wording; the SXE branch in `handleSxeMessage` uses `!isGroupChat && hostFor(...)`, so a discovered room session is never a host). `onConnect` for a MUC answers a `<connect>` with **our current document** (`sendState`) *only if we drew something*; every participant with content answers and each answer **merges**. There is deliberately no `state-offer`/`accept-state` dance in a room — do not reintroduce the 1:1 handshake there (with everyone a host they all offered state and each side overwrote the other's drawing).
- **Snapshots merge, they never clear.** Every document uses the **shared root rid** `SxeDocument.SHARED_ROOT_RID` (`"whiteboard-root"`) so a `<new>`/snapshot from any peer attaches to the same root node. `applyNew` keeps the existing root record (adopts only a *foreign/legacy* root), and `WhiteboardManager.applyState` **must not call `clearShapes()`** — a state snapshot is a union, not a replacement, otherwise receiving a room snapshot wiped the local drawing. Root attributes (`viewBox`/`version`/`baseProfile`) are re-announced by every client, so `applyNew` folds a same-named **root** attribute into the existing one (shape attributes are referenced by rid on the wire and keep their identity).
- **Canvas.** The document is **1280×720** (`WhiteboardView.VIEW_W/VIEW_H`, mirrored in the SVG `viewBox` by `WhiteboardManager`). `onSizeChanged` uses a **uniform "cover" scale** (`max(w/VIEW_W, h/VIEW_H)`, centred) so the board fills the window with **no letterboxing, no distortion** — an ellipse is a true circle and the brush has the same thickness in every direction (the earlier non-uniform x/y scale stretched both; do not reintroduce it). Off-screen parts of the document are reached by panning; the initial fit is reset by the **reset-view** button (`WhiteboardView.resetView()` clears `userMatrix`). **Drawing is clamped to the document:** `beginShape`/`extendShape` clamp every point to `0..VIEW_W`/`0..VIEW_H` and `onDraw` additionally `clipRect`s to the document, so a stroke can never land (or render) outside the board. Rectangle/ellipse track the **drag origin** (`dragStartX/Y`, not the mutated array) so they grow correctly from the touch-down point. Every shape is serialised as one `<path d="…"/>` (local shapes derive `d`, remote shapes are rendered by parsing `d` with `androidx.core.graphics.PathParser`). Tools: pencil / line / **arrow** / rectangle / ellipse (local) + a pan tool; **two-finger pinch zooms and pans** (one finger draws). The arrow (`WhiteboardShape.kind == "arrow"`, `arrowPath`) is a line plus a two-stroke head whose size scales with `strokeWidth`; it is a normal `<path d="…">` so it syncs/selects/moves like any other shape. Widths 1/2/4/8 px, line colour and fill colour via `ColorPickerView` (`hsv-alpha-color-picker-android`); clear/undo/reset view/finish. **The board follows the app theme** (`WhiteboardActivity.applyThemeColors`: paper = `color_background_primary`, grid = a translucent `color_background_tertiary`; the default ink flips to light on dark paper). The toolbar is a modern floating `MaterialCardView` rail **pinned to the bottom-left corner and collapsed by default** (`wb_tools` `visibility="gone"`); the chevron toggle (`wb_rail_toggle`, sits at the *bottom* so the rail grows upwards) expands it (`toggleRail`). Each tool is a `WhiteboardRailItem` (icon button + `WhiteboardRailLabel` name underneath, short labels for narrow entries); the list is a `ScrollView` whose height is clamped in code to the stage so it scrolls instead of overflowing (`clampToolsHeight`, re-run from `addOnLayoutChangeListener` — the activity keeps its view tree across rotation via `configChanges`, so a one-shot `post()` clamp left the list overflowing in landscape; keep the listener). There is **no separate "select" button** — the move tool selects on tap; do not re-add it. Colour buttons show a live swatch of the current colour (`updateColorSwatches`); the line-colour button is a pen-on-underline (`ic_whiteboard_stroke_color`) and the line tool is a diagonal slash (`ic_whiteboard_line`). **Cancel board** is now a **toolbar action** (`menu/whiteboard.xml` `action_whiteboard_cancel`, right-aligned; it was a rail button — do not move it back) handled by `WhiteboardActivity.onOptionsItemSelected` → `cancelBoard`, which clears the drawing — `canvas.clearBoard()` fires `onShapeRemoved` per shape *while the session is still attached*, so the removals are broadcast and the peer's board clears too — then ends the session and `finish()`es. `WhiteboardManager.endSession` (and an inbound `session-terminate`) calls `removeWhiteboardNotice`, which deletes the "Open board" chat message (`Session.noticeUuid`, set in `postWhiteboardNotice`) so the button never lingers for a board that is gone. **The rail follows the theme** (`WhiteboardRailButton`/`WhiteboardRailLabel` use `?attr/text_Color_Main`, the selected tool uses `?attr/whiteboard_selected_background`, the card uses `?attr/whiteboard_rail_background` — both defined per theme in `themes.xml`). The **whiteboard vectors themselves** carry `android:tint="@color/whiteboard_icon"` (a color state list resolving to `?attr/text_Color_Main`); they used to hardcode white, which made them invisible as **menu icons** on a light theme — do not revert to `@android:color/white`. **A long press on any rail button toasts its `contentDescription`** (`wireTooltips`). The sync state is the toolbar **subtitle** (`updateSyncStatus` → `syncStatus.setSubtitle(...)`; there is no floating status pill any more — do not re-add one). Rotations re-attach to the running session via `getSessionForPeer`.
- **Fill bug (fixed).** `WhiteboardShape.isFilled()` must treat a **remote** shape with a non-empty `fill` as filled — it previously only allowed `rect`/`ellipse`, so a fill sent over the wire was parsed but never painted on the receiving side ("заливка не передаётся"). `fill="none"`/empty still means unfilled.
- **Board edits must not request a stream-management ack.** `XmppConnection.sendPacket` asks for an `<r/>` after **every** outgoing `MessagePacket` that has an id (upstream behaviour), and each whiteboard stroke is such a message — so drawing produced a constant `<r/>`/`<a/>` barrage. `MessagePacket` carries a `requestAck` flag (default true); `WhiteboardManager.sendEdits` sends `<state>` edits with `setRequestAck(false)` (the `send(..., requestAck)` overload), while one-off `connect`/`state`/Jingle still ack normally. Do not clear the flag for every board packet, and do not "fix" upstream's per-message ack.
- **Remote transforms must be rendered.** Move/rotate/scale from another client (Stanza) arrives as a `<set>` on the shape's `transform` attr (`transform="matrix(a b c d e f)"`), not as a new `d`. `WhiteboardShape.transform` carries it, `WhiteboardManager.shapes()` reads it (`fromRemote`), and `WhiteboardView.drawShape` parses it (`parseTransform`, `MATRIX_RE`) and `canvas.concat`s it around the path. Without this, remote moves were stored in the SXE document but never drawn (only create/delete rendered) — do not drop the `transform` attribute anywhere along that path. It is also sent back in `attrs()` (empty = identity, skipped on add) so it round-trips.
- **Sending an edit: new attribute ⇒ `<new>`, not `<set>`.** `WhiteboardManager.updateShape` must check `doc.findAttr(rid, name)` first: an attribute that does **not** exist yet (the first `transform` of a shape moved/scaled locally, which `addShape` skipped because it was empty) is a **new record** and has to be announced with `<new parent="…"/>`; only attributes that already exist go out as `<set>`. A `<set>` for a record id the peer has never seen is silently dropped by `applySet` (target not found), so a first move would never reach the other side. `SxeDocument.clearShapes()` and `applyNew` exist for this path.
- **Object tools + text (`WhiteboardView`).** There is **no separate "select" and no "scale" tool** — the single **edit** tool (`wb_tool_move`, labelled *Edit*, the classic four-way-arrows icon `ic_whiteboard_move`) selects on tap, **moves** on drag inside the shape and **resizes** from its handles. `WhiteboardActivity` wires `wb_tool_move` to the tool name `"edit"` (not `"move"`/`"scale"`); `onTouchEvent` routes `"edit"` to `onObjectTouch`. **Eight handles** (4 corners + 4 edge midpoints, `handleAt`/`handleX`/`handleY`) let an element grow/shrink **freely and non-uniformly in any direction**: `beginResize` captures the shape's transform and bounds, `applyResize` computes an absolute scale (`sx`/`sy` per axis, edge handles constrain one axis) about the **opposite handle's fixed anchor** and composes it as `result = startTransform; result.postConcat(scale)` (world-space scale applied *after* the stored transform — do not swap the order). `SELECTION` handles are drawn as eight filled circles with a white ring (`drawSelection`). Dragging moves only when the finger went down on the shape or near the current selection (`transforming = hit != null || isNear(...)`); a tap on empty space just selects. `nearestShape()` still grabs the closest shape when a tap misses. `parseTransform` maps SVG's `matrix(a b c d e f)` to Android's 9-value layout (`[a c e; b d f; 0 0 1]`) — verified with a small JVM harness; do not "simplify" that index mapping or translation silently breaks. **`loadShapes()`** (called on every `onWhiteboardUpdated` and on remote edits) **clears `selected`** (the old shape objects are replaced, so a stale selection would mutate an orphan and render nothing).
- **Sending the board as a PNG (replaces "Done").** The rail button `wb_send` (`ic_whiteboard_send`, *Send*) no longer finishes drawing; it calls `WhiteboardActivity.sendBoardToContact` → `ChooseContactActivity` (single choice, enter-JID allowed, title `whiteboard_send_contact`) with `EXTRA_SHOW_CONFERENCES` and `EXTRA_SHOW_HIDE_OFFLINE` set. The chooser lists **bookmarked conferences** in addition to contacts (so a board can go to a room — `EXTRA_SHOW_CONFERENCES`), and offers a **"hide offline"** menu toggle (`action_hide_offline`, persisted in the `hide_offline` preference, same as `StartConversationActivity`); a picked room is flagged on the result with `EXTRA_PICKED_CONFERENCE` so `onListItemClicked` feeds `renderAndSendBoard(jid, account, muc)`. The JID is resolved with `muc = pickedRoom || isMuc(...) || bookmark != null` (`MODE_MULTI`, else 1:1) and **a confirmation dialog (`whiteboard_send_confirm`)** is shown first; on OK the board is rendered by `WhiteboardView.exportBitmap(2f)` (1280×720 document at 2×, page colour + shapes only — **no grid, no selection handles**) to `files/Files/Sent/whiteboard_<ts>.png`, and `XmppConnectionService.attachFileToConversation(..., "image/png", …)` uploads it (HTTP upload when the account has it). `WhiteboardActivity.onActivityResult(REQUEST_SEND_BOARD)` reads the chosen JID via `ChooseContactActivity.extractJabberIds`. The old `finishDrawing()` was removed (the Send button replaces it).
- **Text tool.** The **text** tool asks a multiline input (`WhiteboardActivity.promptForText`) and `addText` converts each line to glyph outlines (`Paint.getTextPath` per line → `PathMeasure`-flattened contours → `M/L/Z` path data, `nextContour()` so glyph holes survive) stored as an ordinary filled `<path d="…"/>` with a translate `transform`, so text syncs and scales like any other shape (font size `TEXT_FONT_SIZE = 48` document units). Text colour follows the line colour. **`addText` already publishes the shape via `listener.onShapeAdded`, so `promptForText` must NOT call `shareShape` again** — doing so created a second SXE record and the text duplicated (moving updated only one copy, leaving the other behind).

## Message Styling (XEP-0393)

The in-band counterpart to XEP-0394: the directives live **in the body** (`_emphasis_`,
`~strike~`, `` `mono` ``), plus ````` preformatted blocks and `> ` quotations. **Bold is
deliberately not supported** — `*` is ordinary text. Both XEPs
coexist — 0393 styles the body itself, 0394 adds markup for a separate payload; use whichever the
message carries.

- **Parser — `xmpp/styling/MessageStyling`.** `parse(CharSequence)` returns a mixed list of `Span`
  (inline, `start`..`end` **including** both directives) and `Block` (preformatted or quote, with a
  quote `depth` and an optional code `language`). Rules follow the XEP literally: a directive opens
  at the start of the block or after whitespace/another directive and must not be followed by
  whitespace; the close is matched **lazily**, must not be preceded by whitespace, and both
  directives must contain text (empty directives are ignored). Preformatted blocks are literal —
  no child spans — and quotations may nest, so a quote's content is re-parsed past the `>` markers.
  A fence line may only be ``` alone or ``` plus a plain language token: ` ```test``` ` on one line is
  **not** a fence (it would otherwise swallow the whole message into an empty block, which is how the
  outgoing text once disappeared). An empty block (fence with no content) yields no block either.
  `Span` carries its content range separately from the marker range, so marker runs of any length
  (`` `` ``) are stripped correctly.
- **Send:** `Message.applySource` **strips the styling characters** from the outgoing body (`_ ~ `
  and the ``` fence lines, newlines included) so the recipient reads clean text, and derives an
  XEP-0394 `<markup/>` from the parse: inline marks use the span's content range (markers excluded),
  `bcode` covers the code without its fences, `>` lines become `bquote`. Offsets are remapped from
  the source indices to the cleaned indices via a `source -> clean` table, so the markup stays
  correct after the characters are dropped. `*` is *not* a directive (bold was removed) and passes
  through literally.
- **Receive — `Message.renderStyling`** runs in `getSpannableBody` after `renderMarkup`. Inline
  directives become `StyleSpan`/`TypefaceSpan`/`StrikethroughSpan` (applied over the markers too, as
  the XEP recommends); blocks become `entities/StylingSpan.CodeBlock` (monospaced panel) and
  `.Quote` (indent + bar). Every span carries `StylingSpan.STYLING_FLAG` (bit 27) so a re-render
  clears the previous pass. A sender can opt out with an empty
  `<unstyled xmlns='urn:xmpp:styling:0'/>` — `Message.isUnstyled()` makes the renderer skip.
- **The `/me` command is the adapter's job** (`MessageAdapter` → `getMeCommandIndex`, rendered bold
  italic with the nickname). Do not expand it in `renderStyling` too, or it is applied twice.
  `Message.getMeCommandIndex()` must require the command to be a **standalone token at the start of a
  line**: only whitespace may precede it, and it must be followed by whitespace or the end of the
  message. Checking only "some whitespace earlier on the line" is not enough — the `/me` inside
  `https://mega.nz/…` then matched (the space in `"Тест "` satisfied the test) and the link rendered
  as `https://* nickga.nz/…`. The follow-up character check is what makes a bare `/me`, `"  /me x"`
  and a `> quote\n/me x` still work while a URL substring never does.
- **Caps:** `urn:xmpp:styling:0` is advertised in `AbstractGenerator.STATIC_FEATURES`.
- **Not done:** we advertise support and render everything, but the editor has no insertion buttons
  for the directives — a user types them by hand (or pastes them). Ordered lists/nesting limits are
  whatever the XEP allows; there is no per-span "remove styling" UI (the XEP does not define one).

## Message Markup (XEP-0394)

Messages carry semantic markup next to the plain body, in a `urn:xmpp:markup:0` element. Written
from scratch (the earlier attempt was reverted); inline elements are render-only, code blocks can be
authored.

- **Model — `xmpp/markup/MessageMarkup`.** `parse(Element)` reads `span`
  (`emphasis`/`code`/`deleted`), `bcode` (+`language`), `list` (+`ordered`, `li start`) and
  `bquote` into one flat `List<Mark>`; a list item becomes one mark per `li`, so no tree is needed.
  Offsets are **Unicode code points**; unknown elements are ignored and a range with `end < start` is
  dropped. `build(List<Mark>)` writes the element back.
- **Receive — `Message.renderMarkup`** runs in `getSpannableBody` on the plain body. Inline kinds
  become `StyleSpan`/`TypefaceSpan`/`StrikethroughSpan`; blocks become `entities/MarkupSpan`:
  `CodeBlockSpan` (monospaced, block background, **language printed above the first line** —
  `LineHeightSpan` reserves the label row, `LineBackgroundSpan` draws the panel and the label),
  `ListItemSpan` (hanging indent + bullet/ordinal) and `QuoteBarSpan` (quote bar). All carry
  `MarkupSpan.MARKUP_FLAG` (bit 28) so a re-render clears the previous spans first.
- **Send — only code blocks are authored.** `Message.setBody(Spanned)`/`appendBody(Spanned)` run the
  text through `MessageMarkup.parseSource`, which is Telegram-style: lines fenced with ``` open a code
  block, an optional language on the fence line (` ```python `) is stored, the fence lines stay out of
  the body and the block keeps its literal characters. Outside a fence the inline Markdown markers
  `_x_`, `~x~` and `` `x` `` are **stripped** (content kept) so the plain body a receiving client gets
  is clean. The body is marker-free and the `<markup/>` payload is attached alongside it.
- **`entities/MarkupSpan` is drawn, not parsed** — do not put marker parsing back into the render path;
  the single source of the text is the body.
- **XHTML-IM is not rendered or written.** There is no XHTML export any more
  (`de.monocles.mod.SpannedToXHTML` is deleted) and `Message.getHtml()` returns `null` by design, so
  an incoming XHTML-IM payload is stripped at the view layer — the bubble, the chat-list preview and
  the reply fallback all show the plain body. `MessageParser` still parses and keeps the `<html/>`
  element as a payload, and `markMessage` still stores it, but nothing displays it. Do not reintroduce
  a renderer for the stored payload without a reason.
- **Deliberately not implemented:** **bold** (rejected on request — `*` stays literal in both XEPs),
  inline authoring (emphasis/code/deleted), ordered lists and
  nested quotes are shown but not composed in this client.

## File / media sharing — XEP-0385 (SIMS)

The incoming side of Stateless Inline Media Sharing. A peer attaches `<reference xmlns='urn:xmpp:reference:0' type='data'><media-sharing xmlns='urn:xmpp:sims:1'>` to a message; the `<file>` is the ordinary Jingle File Transfer `<file>` element (media-type, name, size, `<hash xmlns='urn:xmpp:hashes:2' algo=…>`, `<desc>`, `<thumbnail>`) and `<sources>` lists one or more `<reference uri=…>` download locations. `urn:xmpp:sims:1` is advertised in `AbstractGenerator.STATIC_FEATURES` (so it is in the caps hash) — do not remove it, or peers stop sending `<media-sharing>`.

- **Model:** `Message.FileParams(Element)` parses the `<media-sharing>` file metadata (size/width/height/duration) and **picks the best source across all `<sources>`** rather than the first one: `sourceRank` prefers an `https?://` URL (3) over `aesgcm://` (2) over `cid:` (1) over an `xmpp:` (Jingle, 0) URI, skipping anything `isUsableSource` cannot fetch. Do not go back to `sources.findChild("reference", …)` (first-child) — a message that lists a Jingle URI before an HTTP URL would then download via Jingle. `getDescription()` reads the XEP-0385 `<desc>`.
- **Typing on receive:** `MessageParser.applySimsType(message)` sets the type from the media-type **before the download**, so a bodyless `<media-sharing>` renders as an image/audio/file immediately instead of as a plain text link (a private MUC message keeps its `TYPE_PRIVATE_FILE`). `Message.getMimeType()` also falls back to the SIMS `media-type` when neither the relative path nor a URL yields an extension. `HttpDownloadConnection.updateImageBounds()` keeps an `image/*` a `TYPE_IMAGE` after the download.
- **Integrity (XEP-0385 §4.2):** after an HTTP download `HttpDownloadConnection.FileDownloader.verifyIntegrityIfNeeded(file)` recomputes the CIDs (`FileBackend.calculateCids` = SHA-256/1/512) and requires one to equal an advertised `Message.FileParams.getCids()`; no match deletes the file and throws `InvalidFileException` (the transfer then shows as failed). It is deliberately **skipped for OMEMO/PGP/decrypted transfers** (their ciphertext differs from the pre-encryption bytes and the envelope has its own MAC) and for a file the app cannot read (scoped-storage MediaStore download). Do not enable it for encrypted transfers.
- **Not done:** resume of a partially downloaded shared media is not hash-checked incrementally; a `cid:` source falls back to the existing `BobTransfer` path, and a Jingle source uses the existing JingleFileTransfer flow.

## Profile cards (vCard)

Full profile cards, modelled on Psi's info dialog (`infodlg.cpp` / `info.ui`): general, work, address, about and photo.

- **`entities/VCard.java`** is the value object. `parse(Element)` understands **both** wire formats; `toElement()` emits **`vcard-temp`** (XEP-0054, what Conversations/Gajim and every Android client speaks, and the only store for MUC rooms) and `toVCard4Element()` emits **vCard 4** (RFC 6350 / XEP-0292) with repeating value elements (`<fn><text>`, `<url><uri>`, `<photo><uri>data:…</uri>`) — note that a value element repeats the property name when both are identical (`<organization><text>…</text>`) but names the type otherwise (`<n><surname><text>…`). A vCard 4 photo is carried as a `data:<mime>;base64,…` URI so one string holds mime + bytes. `N` is split into given/middle/family/prefix/suffix; `EMAIL`/`TEL` keep a simple home/work/cell type + PREF; `ORG`/`ADR` map 1:1 to `<ORGNAME>/<ORGUNIT>` and `<STREET>/<EXTADR>/<LOCALITY>/<REGION>/<PCODE>/<CTRY>`.
- **Service:** `fetchVCard(account, jid, mucRoom, cb)` tries the vCard 4 PEP node first (as Psi does) and falls back to `vcard-temp`; `fetchVCardTemp(account, jid, cb)` reads `vcard-temp` directly; `fetchMucUserVCard(account, nickJid, realJid, cb)` targets the **occupant address `room/nick`** when the real JID is unknown. `publishVCard(account, vcard)` writes `vcard-temp` and, when `features().pepPublishOptions()`, also publishes vCard 4 (an empty card retracts the vCard 4 item so it cannot shadow the cleared vCard 3 card); `publishVCard(account, room, vcard)` writes a room card. `VCardCallback`/`OnAvatarPublication` report results.
- **Rendering on the details screens:** `ui/util/VCardViewBinder.bind(context, container, vcard, onUri)` appends one icon + label + value row per populated field (order mirrors Psi). It is used inline by **`ContactDetailsActivity`** (`profile` / `vcard_fields` section, replacing the old vCard 4 `ListView`) and by **`ConferenceContactDetailsActivity`** for MUC occupants. Email/phone/website rows are tappable (`openVCardValue`); everything else is selectable text. **A card is never fetched for `nick@room` via the bare room JID** — the MUC service answers `room/nick` with that participant's card even when it hides the real JID; the bare room returns the room card instead.
- **Editing your own card:** `VCardActivity` (tabs Общее/Работа/Адрес/О себе/Фото) is opened from the account menu (**Manage accounts → Профиль**, `mgmt_account_profile` → `switchToOwnVCard`) and from the self entry on the details screen (`edit_vcard`). It is editable only for your own account; contacts and MUC occupants are read-only. The account is resolved in `onBackendConnected` (never in `onCreate`, where the service is not bound yet). The photo is managed by `PublishProfilePictureActivity` (XEP-0153), the card itself by `publishVCard`. When the card carries no photo the photo tile falls back to the PEP/local avatar — the account avatar for the own profile, the contact avatar for a roster contact and the room avatar for a room card — and both photo views are `ui/widget/AvatarView` so they follow the global avatar-shape preference (oval / rounded square / square). MUC **room** cards are read-only here (menu `action_view_muc_vcard` in `muc_details.xml` → `switchToVCard(..., mucRoom=true, ...)`); room editing still goes through `ConferenceDetailsActivity`.
- Strings in `values/` (EN) and `values-ru-rRU/` (RU).

## Private notes (XEP-0049 private XML, Psi+/Miranda compatible)

Notes are stored **privately on the server** using **XEP-0049 Private XML Storage** — the exact method used by Psi+'s *Storage Notes* plugin and Miranda IM, so notes synchronise between clients. Namespaces: query `jabber:iq:private` (`Namespace.PRIVATE_XML`), storage `http://miranda-im.org/storage#notes` (`Namespace.NOTES_STORAGE`). The IQ id is the constant `strnotes_1` (`XmppConnectionService.NOTES_ID`), matching Psi+.

- **Wire format** (whole collection in one `<storage>`, tags **space separated**, no ids):
  `<iq type='set' id='strnotes_1'><query xmlns='jabber:iq:private'><storage xmlns='http://miranda-im.org/storage#notes'><note tags='дом работа'><title>…</title><text>…</text></note>…</storage></query></iq>`.
- `entities/Note.java` is the value object (`title`, `List<String> tags`, `body`) plus `parse`, `parseFromStorage(Element query)`, `toStorageElement(List<Note>)` and `matches(needle, Field)` for search (`Field` = `ALL`/`TITLE`/`TAG`/`TEXT`; multiple comma/space separated needles are ANDed, case-insensitive). Because the format has no note ids, each note gets a **content-derived SHA-1 `key`** (`getKey()`); this is what the UI addresses a note by. `List<Note>` lives in memory on the `Account` (`notes`/`notesLoaded`, keyed by `getKey()`).
- **Read/write are full-collection**: `XmppConnectionService.fetchNotes(account)` sends the `<iq type='get'>` (once after login, next to `fetchBookmarks2`) and `processNotesInitial` replaces the set; `saveNote(account, note, replacedKey)` removes the replaced entry, appends the new one, then `pushNotes` sends the whole `<storage>` back via `<iq type='set'>`. `deleteNote(account, key)` is remove + `pushNotes`. Saving requires the account to be `ONLINE` (private XML is server-side); otherwise a toast (`notes_not_connected`/`notes_save_failed`). **Never push a collection that has not been fetched:** because the storage is a single blob, pushing while `!account.areNotesLoaded()` would wipe every note the server holds. `saveNote`/`deleteNote(s)` therefore go through `mutateNotes(account, NoteMutation)`, which queues the change in `mPendingNoteMutations` (keyed by account uuid) and triggers a fetch; `processNotesInitial` applies the queued mutations after `setNotes` and pushes once. `mNotesFetchInFlight` de-duplicates concurrent fetches so a queued mutation just rides along with the response that is already coming. For the same reason a fetch that fails with anything other than `item-not-found` only calls `Account.markNotesLoaded()` and keeps the existing set instead of treating it as empty.
- **Receive:** XEP-0049 responses are routed to the `sendIqPacket` callback, so **no `MessageParser`/PEP event handling is involved** — XEP-0049 has no server push, so a fetch happens on each login only. `Namespace.NOTES_STORAGE + "+notify"` is **not** advertised (no PEP node, no caps change).
- **UI:** `NotesActivity` (list + FAB + plain search box + toolbar **sync** action that re-runs `fetchNotes` + **All tags** action; tags on every card are **clickable chips** that insert the tag into the search field and filter) and `NoteEditActivity` (title / tags / text; save + delete). `TagsActivity` is a separate **tag-only** overview (no titles/bodies) for quick lookup — a `RecyclerView` of tag → note-count rows (alphabetical) with its own tag search, so it stays responsive with thousands of tags; picking a tag returns it to `NotesActivity` via `setResult`/`onActivityResult` and filters there. **Group deletion:** long-pressing a card enters a selection `ActionMode` (title `selected_count`, trash menu item `action_delete_notes`); the confirmation dialog uses the `delete_notes_confirm` plural and calls `XmppConnectionService.deleteNotes(account, keys)`. **Saving a chat message as a note:** the message context menu (`menu/message_context.xml`, item `action_add_to_notes`, hidden by default) has **Add to notes** for both 1:1 and MUC messages — one menu serves both, since `ConversationFragment.populateContextMenu` handles `MODE_MULTI`. It is shown next to copy/select text only when `!encrypted && !m.getBody().isEmpty()`, so PGP/undecrypted content can never be filed. `ConversationFragment.showAddToNotesDialog` opens `layout/dialog_add_to_notes.xml` (title / tags / text, all editable) pre-filled with suggestions the user may override: title = first line of the body truncated to 50 chars (fallback `Conversation.getName()`), text = the full body, tag = the contact display name (1:1) or the room name (MUC) squashed with `singleNoteTag` (storage splits tags on whitespace, so a multi-word name must not silently become several tags). OK is bound after `show()` so an empty note shows `note_empty` without dismissing; saving goes through `XmppConnectionService.saveNote` and toasts `note_added`. There are **no field-scope filters** — the search always matches title/tags/body. All three activities implement `XmppConnectionService.OnNotesUpdated` (auto-registered in `XmppActivity.registerListeners`). Data binding + `NoteAdapter` + `TagAdapter` + `item_note.xml`/`item_note_tag.xml`/`item_tag.xml`. A `ProgressBar` (`notes_sync_progress`) is shown while `!account.areNotesLoaded()`. **Entry point is a bottom-navigation tab** `@+id/notes` (added to all four `bottom_navigation_menu*` menus, handled in `ConversationsActivity`/`StartConversationActivity`/`ManageAccountActivity`/`NotesActivity`). Multi-account: `action_select_account` dialog. Tags are entered space separated (matching storage). Strings in `values/` (EN) and `values-ru-rRU/` (RU).

## XEP-0272 Multiparty Jingle (Muji)

The deepest mod. A mesh audio/video conference per MUC room; `MujiConference`/`MujiConferenceManager` (`eu.siacs.conversations.xmpp.jingle`) own the state, `MujiConferenceActivity` + `MujiParticipantGridView` + `ParticipantView` own the UI.

### Lifecycle, sessions, resources
- **Trigger:** MUC overflow item `action_muji_conference` ("Start group call" / "Group call", `ConversationFragment.toggleMujiConference`) → audio-only / audio+video chooser (`dialog_muji_call_type.xml`) → join and open `MujiConferenceActivity`. Latecomers can join from the `muji_call_bar` panel (see below). Join requests `RECORD_AUDIO` (+`CAMERA` when available) with request code `REQUEST_START_MUJI_CONFERENCE`, plus optional `BLUETOOTH_CONNECT` on Android 12+ (`PermissionUtils.removeBluetoothConnect` keeps it non-blocking).
- All peer connections share one `PeerConnectionFactory`/`EglBase`/microphone track **and one camera track** via `WebRTCResources` (refcounted, `getOrCreateVideoTrack()`, owned by the conference), so the mesh opens one audio device and one camera, not N. MUC presence carries `<muji>` (`Namespace.JINGLE_MUJI`), advertised in caps; per-occupant contents are parsed into `MucOptions.User.getMuji()`.
- An incoming Jingle `session-initiate` with `<muji room>` is only accepted if the sender is an occupant of an active local conference (`JingleConnectionManager.deliverMujiSessionInitiate`), then auto-accepted through a Muji-tagged `JingleRtpConnection` (`isMuji()`); such sessions are excluded from `isBusy()` and never create a Telecom call.
- Muji sessions deliberately **do not create a 1:1 conversation or call-log messages** per participant (`JingleRtpConnection` reuses the MUC `Conversation` and skips `writeLogMessage` when `isMuji()`), so participants don't show up in Chats.
- When a Muji voice chat is created or active in a room, the conversation is **bumped to the top of the chat list** (`Conversation.setMujiCallTimestamp` incorporated into `getSortableTime`/`getSortableTimeExcludingStatusMessages`, set on local join in `MujiConference` and remotely in `PresenceParser` on muji-to-active transitions) so it surfaces like a new message.
- `XmppConnectionService.startForegroundOrCatch` must add `FOREGROUND_SERVICE_TYPE_CAMERA` for video calls/conferences (otherwise background capture fails with `Camera2Session … device policy`).
- Known limitations (stage 4): presence content descriptions still carry no payload-type mapping (codecs are negotiated per-session by WebRTC SDP), and remote audio playout is not explicitly mixed.

### "Video chat" call bar (stage 4)
- Telegram-style `muji_call_bar` panel (added to **both** `layout/` and `layout-land/fragment_conversation.xml` below `muc_topic`, with the ViewPager re-anchored to it) appears/refreshes via MUC-presence → `updateConversationUi()` → `ConversationFragment.updateMujiCallBar()` only when a call is in the room — i.e. this user is in a conference (`isMujiConferenceActive(conversation)`) or any occupant advertises `<muji>` (`mujiParticipantCount` scans `MucOptions.getUsers(false)`).
- Shows "Video chat" + participant count and an accent-filled Join/Open button (`app:backgroundTint="?attr/colorAccent"`, white text, matching the `UnreadCountCustomView` accent convention) pinned to the right edge at 95% of the panel height (set in code); a dismiss "Close" `ImageButton` (`muji_call_bar_close`, X icon) hides the panel until the participant count changes or a conference becomes active (`dismissedMujiCallBarCount`). Tapping Join runs the same `toggleMujiConference()` flow.
- Latecomers who join the room *after* the call started also see the panel: `MujiConference.onOccupantPresence` re-sends our `<muji>` presence the first time it sees an occupant who is not in the call (so servers that do not replay custom elements still deliver it), and `PresenceParser` calls `updateConversationUi()` whenever an occupant's `<muji>` changes (previously only on user-count/online/status changes, so a call starting in a full room did not refresh the panel).
- If the conference can't start (`WebRTCResources.create` fails → conference removed from the registry) or the audio/video chooser dialog ends in a permission denial, the fragment **does not open `MujiConferenceActivity`** — instead `NotificationService.notifyMujiJoinFailed(res)` posts a heads-up on the dedicated `muji` channel (`MUJI_CHANNEL_ID`, `MUJI_NOTIFICATION_ID`) without raising a new window.

### Controls, self-view, mic/video mute
- The control bar is a **centred compact group** (`muji_controls`: `layout_width="wrap_content"` + `layout_gravity="center_horizontal"`, each button `layout_marginHorizontal="6dp"`), so the **red hang-up button (`muji_leave`) always sits exactly in the centre** of the group with mic/camera to its left and speaker/"More" to its right, evenly spaced on any screen width; the visible buttons are **mic / camera / hang-up / speaker / "More"** and are all always shown (`View.VISIBLE`) while a conference is active — the camera button is no longer hidden for audio-only (only the toolbar is hidden while the conference is active). Do not wrap the row in a `HorizontalScrollView`, do not give the buttons `layout_weight`, and do not reorder the slots (all three made the spacing uneven).
- **Secondary actions live in a "More" icon popup** (`muji_more` → `MujiConferenceActivity.showMoreMenu`, `layout/popup_muji_more.xml`): **switch camera** and **whiteboard** as **stand-alone round buttons styled exactly like the main call controls** (`MujiCircleButton`: grey `#525252` circle, white icon), stacked **vertically**. The popup root is a plain transparent `LinearLayout` — there is **deliberately no shared card/plate behind them** (an earlier `MaterialCardView` surface and a "flat, no-plate" `MujiFlatButton` variant were both removed on request), so each button shows only its own circle. It is a plain `PopupWindow` (not a `PopupMenu`, whose items would render as text rows). Positioning is done **explicitly with `showAtLocation` in screen coordinates** (never `showAsDropDown`): the popup is measured with `AT_MOST` against `DisplayMetrics` (`setWidth`/`setHeight` capped to it), its bottom edge is placed `margin` above the **top** of the "More" button so it **never covers the button** (a `showAsDropDown` anchor sits at the button's *bottom* edge, so the old negative offset left the popup overlapping it), and both axes are clamped into `getWindowVisibleDisplayFrame`; if there is no room above, it is placed below the button instead. Do not go back to `showAsDropDown`, do not drop the `anchor.getHeight()` term, and do not re-add a popup background plate. There is no `menu/muji_conference.xml` any more — do not reintroduce a text menu.
- **The control bar is scaled down only when it would not fit.** `MujiConferenceActivity.fitControlBar()` runs once from `onCreate`: five 56 dp buttons with 6 dp margins are 340 dp, more than the ~320 dp of the smallest supported displays, which would clip the outermost buttons; if `count * (size + 2*margin)` exceeds the available width the gaps tighten (2 dp) and the buttons shrink (down to 36 dp) to fit, otherwise nothing changes. The centred-group look on normal screens is untouched.
- **Switch camera works in a solo call too, and survives the camera being off.** `MujiConferenceActivity.isCameraSwitchable()`/`switchCamera()` delegate to `MujiConference.isCameraSwitchable()`/`switchCamera()`, which use the shared `WebRTCResources` — not the per-participant `JingleRtpConnection`s. Two traps, both fixed: (1) the old per-connection check (`connection.getLocalVideoTrack().isPresent() && connection.isCameraSwitchable()`) reported false with **zero participants**; (2) the shared camera only exists once video is actively contributed (`WebRTCResources.getOrCreateVideoTrack` is lazy), so a check against it is also false while the camera is switched **off** — exactly when the user reaches for the flip. Both `MujiConference.isCameraSwitchable()` and `WebRTCResources.isCameraSwitchable()` therefore fall back to `VideoSourceWrapper.deviceHasMultipleCameras(context)` (a cached `Camera2Enumerator`/`Camera1Enumerator` device-name count, no capture started); `MujiConference.switchCamera()` also calls `getOrCreateVideoTrack()` first so the flip is not a silent no-op before video was switched on. `showMoreMenu` shows the button whenever that reports multiple cameras. Do not go back to a connection/wrapper-only check. `ic_flip_camera_android_black_24dp` is tinted with `@color/whiteboard_icon` (`?attr/text_Color_Main`) so it stays visible in the popup on light and dark themes.
- **Self-view tile** (`SELF_KEY`, label "You") renders the shared local camera track (`MujiConference.getLocalVideoTrack()`, mirrored on the front camera) whenever the conference was joined with video. When nobody else has joined yet the UI shows the same grid + controls (mic/camera/speaker visible; state taken from the self tracks via `updateControls`), so a solo call looks exactly like a call with two or more participants.
- The mic button works even with no participants: `MujiConferenceActivity.toggleMicrophone` delegates to `MujiConference.setMicrophoneEnabled`/`isMicrophoneEnabled`, which mute/unmute the **shared conference `AudioTrack`** (`WebRTCResources.audioTrack`) — the same track every peer session references, so the mute persists for participants joining later.
- **Camera off** falls back to the avatar: `MujiConferenceActivity.toggleVideo` removes `Media.VIDEO` from the `MujiConference` media (re-sent in the `<muji>` presence so remote tiles pick it up) while keeping the shared track alive; `bindVideo`/`bindSelfVideo` treat a participant/user that no longer advertises video as avatar-only. Turning video back on re-adds `Media.VIDEO` and re-enables the track/camera. With **no participants yet** `toggleVideo` toggles the local media + shared `VideoTrack` directly (and asks for `CAMERA` first, `REQUEST_CAMERA`), so an audio-only conference can be upgraded to video from the always-visible button. Speaker (`muji_speaker`) toggles `AudioManager.setSpeakerphoneOn` in `MODE_IN_COMMUNICATION` (off by default; theme accent tint when on).

### Grid, tiles, expand
- One tile per participant (`MujiParticipantGridView`, a plain `ViewGroup` — deliberately not a `RecyclerView`, to avoid recycling the video renderers), each bound to that connection's `getRemoteVideoTrack()`.
- No `ScrollView`; `MujiParticipantGridView.onMeasure` fills the whole remaining area — it picks the column count whose cells come closest to the video's 16:9 aspect ratio (small penalty for a partial last row, which is stretched to full width), so tiles always tile the area with no empty space (video centre-cropped to the cell, avatars centred).
- **Tap-to-expand:** tapping any participant or self tile expands it to fill the grid; the remaining participants render as **floating round avatar thumbnails** (no frame/background) in a vertical column to the left, overlapping the expanded tile; a second tap collapses. `MujiParticipantGridView.setExpandedChild()` tracks the expanded child; thumb width = min(30% grid width, 180 dp), 16:9. `ParticipantView.setThumbnailStyle(boolean)` toggles full tile (label, 96 dp avatar, `color_background_secondary` background) vs thumbnail (label hidden, transparent, 48 dp avatar; renderer + speaking border clipped to a centred 48 dp circle via `setCircleDiameterPx(int)`). `MujiConferenceActivity.applyExpandedStyling()` is called from `refresh()` and the tap listener to keep styles in sync.
- **Z-order fix:** in expanded mode thumbnails (self is always child index 0) overlap the expanded tile, which is a later child and would otherwise be drawn on top of them, hiding the self tile. `applyExpandedStyling()` raises each thumbnail's `translationZ` (2 dp on the tile root; tiles use `TextureViewRenderer`, a normal view, so ordinary Z ordering applies) above the expanded tile; on collapse every tile's Z resets to 0.
- Muji tiles use a custom `TextureViewRenderer` (`ui/widget/TextureViewRenderer.java`, an `EglRenderer`+`SurfaceTexture` renderer modelled on Signal's) instead of `SurfaceViewRenderer`: a `SurfaceView` cannot be clipped to a circle and lives in its own compositor layer, so it could not render circular video thumbnails. It fills the view centre-cropped via `EglRenderer.setLayoutAspectRatio(viewAspect)` (no `setScalingType`/hardware-scaler, so the old `BLASTBufferQueue … rejecting buffer` `SurfaceViewRenderer` workaround no longer applies to Muji; `RtpSessionActivity` still uses `SurfaceViewRenderer` and keeps it).

### Avatars and speaking indicator
- Tiles without a remote video track show the occupant's **avatar** instead of a black tile (`MujiConferenceActivity.bindVideo` → `showAvatar`; circular `ShapeableImageView` styled with `ShapeAppearanceOverlay.PhotoRound`, loaded via `AvatarWorkerTask` from the matching `MucOptions.User`; tile background `?attr/color_background_secondary`). `participantAvatarable` also falls back to the roster `Contact` for the participant's real JID when no `MucOptions.User` matches.
- **Speaking indicator:** `MujiConferenceActivity` polls `JingleRtpConnection.getRemoteAudioLevel` every 10 ms (`WebRTCWrapper` reads the loudest `audioLevel` from per-peer stats, skipping our own `media-source`), and `ParticipantView.updateSpeakingIndicator()` runs a `ValueAnimator` — around the avatar (scale 1.0→1.05, stroke = 5% of the avatar size) when no video is shown, or an alpha pulse of a green `SpeakingBorderView` around the video tile (rounded rectangle for a full tile, circle for a thumbnail) when the renderer is visible. `setSpeaking`/`showAvatar`/`showRenderer` all call it, idempotently so a running animation is never restarted. Gated by the `play_gif_inside` preference ("play animated images").

### Video-capability fallback (avatar vs black tile)
- `MujiConferenceActivity.remoteProvidesVideo`: when the last `<muji>` a participant advertised is only a `<preparing/>` placeholder (or absent) — which happens for the party *already in the room* when the other joined, because the newcomer's active voice/video presence is not reliably delivered to it — the tile does **not** trust the capability element; it falls back to the resolved Jingle session, so a received remote video track (`JingleRtpConnection.getRemoteVideoTrack()` / `WebRTCWrapper.remoteVideoTrack`) is authoritative and video shows.
- For a **totally absent** `<muji>`, the two cases are told apart with `MucOptions.User.hasEverSeenMuji()` (`mujiSeen`, sticky set on the first non-null `setMuji`): if the occupant *ever* advertised a conference and now no longer does, they left the call — the stale renderer must fall back to the **avatar** (otherwise the dead session renders a black window); if we *never* received any muji presence from them (join-while-in-room), the session is authoritative and video shows. An explicit active `<muji>` without video (camera toggled off) still forces the avatar — do not "fix" that back.
- Independently of presence, a tile falls back to the avatar when its bound video track stops delivering frames: `framesLively` treats a track as dead after `FRAME_TIMEOUT_MS` (3 s) without a frame, and a track that never delivered a first frame after `FIRST_FRAME_GRACE_MS` (5 s) after (re)binding — covers a remote disabling the camera when its `<muji>` update is lost, and prevents a permanently black tile when a renegotiated track never renders (self tile uses the same check).
- Because WebRTC keeps producing **black frames** when a remote disables its camera (it does not stop the stream), `framesLively` also treats a track as dead after `BLACK_FRAME_TIMEOUT_MS` (2 s) of continuously black frames: the frame sink samples the I420 luma at most once per `BLACK_FRAME_CHECK_INTERVAL_MS` (1 s), and `isBlack()` compares average luma against `BLACK_FRAME_LUMA_THRESHOLD` (24). This is what makes the avatar appear on the *other* devices when the MUC server does not rebroadcast the camera-off `<muji>` presence.

### Audio routing, chime, wakelock, logging
- **Join/leave sounds are muted for Muji** (`CallIntegration.setAudioCuesEnabled(false)` on every Muji-tagged `JingleRtpConnection`, plus `CallIntegration.playMujiJoinSound()` for the one-off chime): the `connected.ogg` beep, ring-back, drop/busy/error tones no longer fire per peer session on every device. The only audible cue is a single join chime decided by `JingleRtpConnection.shouldPlayMujiJoinChime` → `MujiConference.shouldPlayJoinChime(locallyInitiated)`, gated by `existingMujiParticipantsAtCreation`: the **conference starter** (count 0) hears a chime when the **first** participant joins; a **later joiner** (count ≥ 2) hears one when their first locally-initiated session connects; the **first joiner** of an empty-looking call (count 1) stays silent — claimed once per conference via an `AtomicBoolean`. Established participants and non-joining MUC members stay silent; no drop tone on leave.
- **Bluetooth routing lives entirely in `MujiConference`** (`initAudioRouting()` from `join()`, teardown in `leave()`), so it **survives activity destruction** — leaving the voice-chat window keeps the call running in the background with BT headset audio/mic. On API 31+ it uses `AudioManager.setCommunicationDevice()` (legacy `startBluetoothSco()`+`setBluetoothScoOn()` only below S), requested when the speaker is off (delegated from `MujiConferenceActivity.toggleSpeaker()`), tracked via an `ACTION_SCO_AUDIO_STATE_CHANGED` receiver on the application context (unregistered in `leave()`), and released (`clearCommunicationDevice`) when the speaker is on or the conference ends — otherwise it falls back to the earpiece. A dropped SCO connection is **re-requested** while the call is active and speaker off (bounded `MAX_SCO_RETRIES`/`SCO_RETRY_DELAY`, reset on connect or a manual speaker toggle).
- A BT headset connecting *after* the conference starts triggers `ACTION_ACL_CONNECTED` → retry budget reset + `requestBluetoothRouteRetry` (delayed retries until the BT audio profile is up). On devices that do not deliver `ACTION_ACL_CONNECTED` (Android 13+/EMUI), a periodic `bluetoothRoutingRunnable` (every 2 s) calls `requestBluetoothSco()` — silent when no BT device is present, logs only on successful routing — so a mid-call headset is picked up within ~2 s. The poll also detects the headset disappearing and resets `scoRequested`, since the legacy `ACTION_SCO_AUDIO_STATE_CHANGED` broadcast does not fire on the `setCommunicationDevice()` path.
- A **partial wakelock** (`POWER_MANAGER.PARTIAL_WAKE_LOCK`, tag `monocles:MujiConference:<room>`) is acquired in `initAudioRouting()` and released in `leave()` so screen-off does not stall the WebRTC audio path.
- Debug builds write a stanza/camera trace to `files/muji.log` via `MujiLog.log(filesDir, msg)` (Huawei/EMUI strips `Log.d` from logcat; read with `adb shell run-as de.monocles.mod cat files/muji.log`). **Note:** `MujiLog.log()` is the *only* thing that reaches that file — plain `Log.d`/`Log.w` do not — and it is a no-op unless `BuildConfig.DEBUG` and `filesDir` is non-null. `MujiConference.logBt()` is the Bluetooth-route helper; it writes **only to `MujiLog`** (not to logcat).
